# Does VS Code for the Web load the plugin?

Stage 3a of [`docs/playground-bridge.md`](../../playground-bridge.md) §4, measured before any web
build of the extension is written.

Question: does VS Code for the Web load a TypeScript server plugin that a web extension contributes
through `contributes.typescriptServerPlugins`, and what must the extension ship?

Date of the run: 2026-09-29.

## Answer

**Loads.** VS Code for the Web 1.139.1 loads a plugin contributed by a web extension into its
TypeScript 6.0.3 web server, `create()` runs, and a decorated `getSyntacticDiagnostics`,
`getSemanticDiagnostics` and `getQuickInfoAtPosition` are visible through
`vscode.languages.getDiagnostics` and the hover provider. It loaded as an **ES module with a default
export** and did **not** load as CommonJS. So per §4 of `docs/playground-bridge.md`, the first branch holds: the
web build is the desktop one with a `browser` entry and the service bundled as ESM. The caveats
(cross-origin isolation, the injected `typescript`, file reads) are in "What the web build needs".

## How the web host loads a plugin (read from the shipped bundles)

`extension.js` (typescript-language-features, browser build) collects every extension's
`contributes.typescriptServerPlugins` and, on web, passes each extension's **URI** (not a file path)
as a probe location:

```
--globalPlugins <names>   --pluginProbeLocations <extension uri, ...>
```

`tsserver.web.js` then imports the plugin with its own web host (`importPlugin`, quoted from the bundle):

```js
importPlugin: async (root, moduleName) => {
  let packageRoot = combinePaths(root, moduleName); // <probe location>/node_modules/<name>
  let pkg;
  try {
    pkg = await (await fetch(combinePaths(packageRoot, 'package.json'))).json();
  } catch {
    return {
      module: undefined,
      error: new Error("Could not load plugin. Could not load 'package.json'."),
    };
  }
  let browser = pkg.browser;
  if (!browser)
    return {
      module: undefined,
      error: new Error("Could not load plugin. No 'browser' field found in package.json."),
    };
  let url = combinePaths(packageRoot, browser);
  try {
    let { default: m } = await import(url);
    return { module: m, error: undefined };
  } catch (e) {
    return { module: undefined, error: e };
  }
};
```

So the contract is: `<extension root>/node_modules/<plugin name>/package.json` with a `browser` field,
naming a file that is `import()`ed as an ES module whose **default export** is the plugin init
function (`function init(modules) { return { create(info) { ... } } }`).

## What was run

Everything is in this directory. `ext/` is generated by `make-ext.mjs <variant>` (a web extension
with `"browser": "./extension.js"`, `contributes.typescriptServerPlugins: [{ name, enableForWorkspaceTypeScriptVersions: true }]`
and the plugin package under `ext/node_modules/<name>/`); the plugin decorates
`getSyntacticDiagnostics` (adds `TSHADE_PROBE_SYNTACTIC`), `getSemanticDiagnostics` (adds
`TSHADE_PROBE_SEMANTIC`) and `getQuickInfoAtPosition` (appends `TSHADE_PROBE_QUICKINFO`) on `.ts`
files and logs through `info.project.projectService.logger` and `console`. `tests/index.js` (copied
to `ext/test/index.js`, because the ext host only runs a test module that sits inside the
extension) opens `a.ts` from the mounted `folder/`, polls `vscode.languages.getDiagnostics` for up to 60 s
for `TSHADE_PROBE`, then asks `vscode.executeHoverProvider` at `answer`.

Setup that the proxy and the Chromium revision needed:

```bash
npm init -y && npm i @vscode/test-web@0.0.81
# the build, downloaded by hand (test-web's own download works from a cache directory of this name):
curl -sS https://update.code.visualstudio.com/api/update/web-standalone/stable/latest   # -> commit, url, sha256
curl -sS -L -C - --retry 20 --retry-delay 2 --retry-all-errors -o dl/vscode-web.tar.gz \
  https://vscode.download.prss.microsoft.com/dbazure/download/stable/04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1/vscode-web.tar.gz
```

## What was observed

Results with `--coi` (six variants, one run each; `run-<variant>.log`):

| Variant         | Plugin package                                                                                  | Result                                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `esm`           | `plugin.mjs`, `export default init`, `"browser": "./plugin.mjs"`, `"type": "module"`            | **loads**, all three effects seen                                                                                 |
| `esm-scoped`    | the same under `node_modules/@typeshade/web-probe-plugin` (the scope of the real plugin's name) | **loads**                                                                                                         |
| `esm-js`        | ES module syntax in `dist/plugin.js`, no `"type"` field                                         | **loads** (the browser ignores `"type"`; any JS file served as a module works)                                    |
| `esm-multi`     | `plugin.mjs` with a static `import './helper.mjs'`                                              | **loads**, helper fetched and run (`[probe-plugin] helper.mjs was imported`), so a bundle may be split into files |
| `esm-nobrowser` | same as `esm` but no `browser` field (only `main`)                                              | **does not load**: package.json fetched, plugin file never requested                                              |
| `cjs`           | `plugin.js` ending in `module.exports = init`, `browser` set                                    | **does not load**                                                                                                 |

The second candidate location (`/../../..`, the parent of the tsserver bundle) always fails with
"Could not load 'package.json'"; that line is noise. For `esm-nobrowser` the channel showed
`Couldn't find typeshade-web-probe-plugin` and no diagnostic appeared in 60 s; the "No 'browser' field"
message itself is from the bundle's source (above), the top of that log was scrolled out of my reader
(`output-esm-nobrowser.txt`), so that one line is not quoted from a run.

Without `--coi` (`run-esm-nocoi.log`, `crossOriginIsolated=false`, no `SharedArrayBuffer`): the plugin still
loads, but only **once** (one server, the syntax one), `getSemanticDiagnostics` is never called, only
`TSHADE_PROBE_SYNTACTIC` and the quick info marker appear, and inside `create()` the environment probe reads

```
[probe-plugin] env: readFile via serverHost length=undefined fileExists=false | fetch=function importScripts=function Worker=function WebAssembly=object SharedArrayBuffer=undefined crossOriginIsolated=false require=undefined process=undefined self=object
```

whereas with `--coi` the same line reads `readFile via serverHost length=106 fileExists=true ... SharedArrayBuffer=function crossOriginIsolated=true`.
The web TypeScript extension's file system bridge and cancellation both use `SharedArrayBuffer` and `Atomics.wait`
(seen in `extension.js`), which is why project-wide IntelliSense needs it. I did not measure vscode.dev or
github.dev themselves (no network route to run them here); whether they are cross-origin isolated for the
extension host is therefore **not established here**, only that a page that is not isolated gives the
syntax-server-only behaviour above.

Not tested: a manifest that contributes `typescriptServerPlugins` **without** a `browser` entry. The web
extension host only runs extensions that have one (the Web Extensions guide the design cites says the same),
so the TypeScript extension cannot see such a manifest's contribution on web; a probe of it would need a
second extension to host the test, and was left out.

## What the web build of vscode-typeshade would therefore need

1. A **`browser` entry** in the extension manifest (any activation code; the plugin does not need it to
   run, but without it VS Code does not treat the extension as a web extension and the contribution is
   never read). Keep `main` for desktop; both can coexist.
2. `contributes.typescriptServerPlugins` naming the plugin (the scoped `@typeshade/tsserver-plugin` works).
3. The plugin package at **`<extension root>/node_modules/<plugin name>/`** with a `package.json` that has a
   **`browser`** field (a `main` alone is ignored on web), pointing at an **ES module whose default export is
   the plugin init function**. Not CommonJS: a `module.exports` bundle throws `module is not defined` when
   the worker `import()`s it. The file may be `.js` or `.mjs`, and may import sibling files by relative path.
   It must ship inside the packaged VSIX: `node_modules` must not be excluded by `.vscodeignore`, and
   `scripts/package-extension.mjs` has to place the plugin there (the desktop layout already has it).
4. The service **bundled as a browser ESM** (no `require`, no `process`, no Node built-ins; inside the
   plugin worker `require` and `process` are `undefined`, `fetch`, `importScripts`, `Worker`, `WebAssembly`
   exist). The plugin must use the `typescript` instance passed to `init(modules)` (6.0.3 here), not bundle its
   own, and must tolerate being created twice, once in a `partialSemantic` syntax server and once in the
   semantic server.
5. **File reads through `info.serverHost`** (`readFile`, `fileExists`, ...), not `fs`: with cross-origin
   isolation they returned the mounted file (length 106), without it they returned nothing. The plugin's
   worker has no `vscode` API, so anything the plugin reads goes through `serverHost` (or `fetch`); only the
   extension host side (the panel) can use `vscode.workspace.fs`. The design's sentence "the file reader
   going through `vscode.workspace.fs`" therefore holds for the panel, not for the plugin.
6. **Cross-origin isolation** of the page for semantic diagnostics: without `SharedArrayBuffer` only the
   syntax server exists and `getSemanticDiagnostics` is not called, so a plugin that replaces semantic
   answers has no effect. Check vscode.dev and github.dev for this before promising the web build (not
   measured here).
7. A test for it: this probe is the shape (`@vscode/test-web`, `--coi`, a mounted folder, poll
   `getDiagnostics`); it ran in about 3 s of polling once the workbench was up, and a run takes about a minute
   with the build cached.

Files here: `make-ext.mjs`, `run.sh`, `serve.sh`, `driver.mjs`, `tests/index.js` and `folder/`,
which are enough to run it again, and `output-esm.txt` and `output-cjs.txt`, the TypeScript Server
Log lines quoted above. The generated `ext/`, the Chromium revision shim, the full `run-*.log` logs
and the screenshots stayed on the machine that ran it: they are regenerated by the commands above.
